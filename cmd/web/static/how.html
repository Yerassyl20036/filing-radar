How it works

Filing radar reads every new SEC filing within minutes, explains what changed with a source for every claim, and checks each prediction against how the stock actually moved the next day. Below is how it's built, what's live today, and what comes next.

Where the results go

Raw first, analysis later. A filing shows up in the feed within a minute, straight from EDGAR. Each tracked filing then gets one Temporal workflow, with the accession number as the workflow ID, so no filing is ever analysed twice. The workflow writes its label, and for an 8-K the model's score, to a triage table; a high 8-K then gets a note in a notes table, under the same accession number, and the feed shows both on the filing's row once they land. Temporal never serves visitors: the website reads only Postgres, so if Temporal is down, the feed still works.

What happens to one filing

  1. 1
    Fetch.

    Every minute the worker reads EDGAR's latest-filings feed, pages back until it reaches filings it already has, and stores each new one once, keyed by its accession number.

    stage 1, live
  2. 2
    Triage.

    Plain rules read the 8-K item numbers (4.02 restatement, 2.02 earnings, 5.02 an executive leaving…) and label every filing high, medium, low or routine. Then a language model (DeepSeek by default, Claude as an option) reads each 8-K and scores it from 0 to 100, with a one-sentence reason and a quote. The quote must appear word for word in the filing, or the score is dropped. The model can raise a label, never lower it, and a daily cap bounds the cost.

    stage 2, live
  3. 3
    Analyst agent.

    For each high-importance 8-K: compare it with the company's previous comparable 8-K and write a headline and 2 to 5 claims on what changed, each quoting the document it comes from.

    stage 3, live
  4. 4
    Check.

    Code, not the model, checks that every quote appears word for word in its source. Claims that fail get one repair; if they fail again they're dropped. With fewer than 2 checked claims left, the note is not published.

    stage 3, live
  5. 5
    Publish.

    The note appears in the feed with links to the original filing on sec.gov.

    stages 1–3, live
  6. 6
    Score.

    A Temporal workflow waits until after the next market close, fetches the price move, and checks the prediction. Scores are public.

    stage 4

Live today: stage 0 (the three servers, the deploy pipeline, the tunnels, the health checks), stage 1, the filing feed, stage 2, the rules and the model that label it, and stage 3, the notes on high 8-Ks. Stage 4 comes next.

How a note is written

The dispatcher finds high 8-Ks without a note and starts one workflow for each, with the workflow ID NOTE- and the accession number, so a filing never gets two notes. The steps are fixed: the model drafts, code checks, and the model gets one chance to repair what failed. A note that keeps fewer than 2 checked claims is saved as rejected, with its reason, and never shown.

The model writes; code checks every quote against the filing's text One workflow per filing, so a note is written at most once

Data sources

  • EDGAR latest filings — the live feed the worker polls every minute.
  • EDGAR daily index — every filing of each day, used to repair gaps.
  • SEC developer resources — the access rules: a declared User-Agent and at most 10 requests per second. The radar stays under 1.

Decisions

  • Three servers with 1 GB of RAM each. Go binaries use tens of MB and Temporal's single-binary server under 100 MB, so Kubernetes would cost more than everything else combined.
  • No database port on the internet. The worker reaches Postgres and Temporal through SSH tunnels; each tunnel key may open exactly one port on one machine.
  • A model only where rules can't decide. Item numbers and form types are rules; only 8-Ks go to the model, under a daily cap.
  • The model is swappable. The workflow talks to one small interface (score, reason, quote), so DeepSeek and Claude are two implementations chosen by configuration. Filings are public data, so the choice is about cost and quality, not privacy.
  • The model can raise a label, never lower it. A restatement stays high even if the model shrugs; the model's job is to catch what rules can't read, like big news filed under 8.01 Other events.
  • Every score carries a quote that's checked. The quote must appear word for word in the filing, or the score is dropped. It's the first piece of stage 3's rule that every claim is cited and verified.
  • Every claim is checked before it's published. A note whose citation doesn't match the filing's text is retried or dropped.
  • A workflow, not a free-roaming agent. The note's steps are fixed: gather, draft, check, repair once. The model never decides what to fetch or when it's done, so a note's cost and running time have a ceiling, and every step is visible in Temporal.
  • One repair, then drop. A failed quote goes back to the model once, with what didn't match. A second failure means the claim isn't in the source, so it's dropped rather than retried until it happens to pass.
  • A daily dollar budget. Every model call is recorded with its tokens and cost. When the day's budget is spent, calls stop until midnight UTC and the rules' labels stand; the status page shows today's spend.
  • Store a filing only after paging stops. EDGAR lists a filing once per party, and a Form 4's two entries can land on two pages. Storing page by page would mistake the second half for "already stored", stop paging early and skip filings.
  • Temporal for waiting, not for everything. The one-minute poll is safe to repeat and needs no workflow engine; the next-day score has to survive restarts, so it gets one.
  • One Temporal workflow per tracked filing. The workflow ID is the accession number, so Temporal refuses a second start; a dispatcher retries anything without a label every minute. Form 4s and other routine forms are labelled on the spot and never start one.
  • Deploys by hand, from main only. The pipeline ends by proving the worker reached both other servers.

Development

Built in about three days with Claude Code (Claude Opus 5.5, with a little Claude Haiku 5.5) as the main developer, under the owner's direction. Measured from the session transcripts: about 1.0 million output tokens and 219 million cached-context tokens across 710 model responses, roughly $82 at Anthropic's API list prices. It was paid through a Claude subscription, not per token, so the $82 is what the same work would cost at list rates, not what was billed.

Built with

  • Temporal — durable workflows for each filing and note.
  • DeepSeek API — the default language model.
  • SEC EDGAR APIs — the filings themselves.
  • Go — the web server and the worker.
  • PostgreSQL — filings, labels, notes and model calls.
  • Caddy — HTTPS in front of the website.
  • Oracle Cloud Free Tier — the three servers.
